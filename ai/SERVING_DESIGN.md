# 이미지 생성 서빙 설계 (초안) — 메시지 큐 + 노트북 워커 + API 대체

일기가 저장되면 Java 백엔드가 이미지 생성을 **비동기로** 요청한다. 노트북 GPU가 살아 있으면 노트북에서 LoRA 모델로 만들고, 노트북이 꺼져 있거나 일이 밀려 있으면 외부 이미지 API로 만든다.

- 상태: **보류 (2026-10-27)**. 서비스 아키텍처가 바뀔 예정이라 이 설계는 진행하지 않는다. 5장의 묶음 처리 시간표와 7장의 GPU 메모리 표는 새 설계에서도 참고할 수 있다. 팀이 결정할 항목은 9장에 모았다.
- 성능 수치는 10/23 실측(`results/inference_summary.csv`, `outputs/runs/*/log.txt`)과, 그 실측을 바탕으로 한 **추정**이다. 추정은 따로 표시했다.

## 1. 결론 요약

| 항목 | 정한 방향 |
|---|---|
| 큐 | RabbitMQ (TTL과 dead-letter가 기본 기능). AWS면 SQS + Lambda로도 가능 |
| 대체 기준 | 노트북 큐에서 **60초 넘게 대기**하면 자동으로 API 큐로 이동. 노트북 heartbeat가 끊기면 Java가 처음부터 API 큐로 보냄 |
| 노트북 워커 | 큐에서 **가져가는(pull)** 방식. 요청을 짧게 모아서 한 번에 처리. 트랜스포머는 gguf_q4 |
| 결과 전달 | 이미지는 S3(저장소)에 올리고, 결과 메시지에는 URL만 담음 |
| 처리 완료(ack) | 업로드가 끝난 **뒤에** 보냄. 중복 결과는 `job_id`로 무시 |
| 6GB 처리량 | 1건씩 처리하면 장당 약 30~50초(추정). 40건 묶음이면 장당 **약 16초(실측)** |

## 2. 전체 구조

```
                          ┌──────────── heartbeat (30초마다) ───────────┐
                          ▼                                             │
┌──────────┐  publish  ┌──────────────────┐  consume (pull)   ┌────────┴─────────┐
│  Java    │ ────────▶ │ image.local 큐   │ ────────────────▶ │ 노트북 워커       │
│  백엔드   │           │ (TTL 60s)        │                   │ klein + LoRA, q4 │
└────┬─────┘           └───────┬──────────┘                   └────────┬─────────┘
     │                         │ 60초 안에 안 읽히면                      │
     │ heartbeat 끊김 →        ▼ dead-letter로 자동 이동                 │
     │ 처음부터 여기로   ┌──────────────────┐  consume   ┌──────────────┐ │
     └───────────────▶ │ image.api 큐      │ ─────────▶ │ API 워커      │ │
                       └──────────────────┘            │ (서버, 항상 켜짐)│ │
                                                       └──────┬───────┘ │
                                                              │         │
                         ┌────────────┐   upload              ▼         ▼
                         │    S3      │ ◀───────────────── 이미지 업로드
                         └────────────┘
                                │ URL
                                ▼
┌──────────┐  consume  ┌──────────────────┐
│  Java    │ ◀──────── │ image.result 큐  │ ◀── 두 워커 모두 결과를 여기로
└──────────┘           └──────────────────┘
```

**pull 방식이 노트북에 맞는 이유**
- 노트북이 큐 서버에 **먼저 접속해서** 메시지를 가져간다.
- 그래서 노트북에 공인 IP나 포트 개방이 필요 없다. 공유기 뒤에 있어도 된다.
- 노트북이 죽어도 메시지는 큐에 남는다.

## 3. 메시지 설계

### 3-1. 큐

| 큐 | 생산자 | 소비자 | 설정 |
|---|---|---|---|
| `image.local` | Java | 노트북 워커 | `x-message-ttl: 60000`, `x-dead-letter-routing-key: image.api` |
| `image.api` | Java, dead-letter | API 워커 | TTL 없음 |
| `image.result` | 두 워커 | Java | |
| `image.dlq` | 재시도 초과 | 사람이 확인 | 실패가 3번 넘으면 여기로 |

### 3-2. 요청 메시지 (Java → 워커)

```json
{
  "job_id": "diary-1234-v2",
  "diary_id": 1234,
  "user_id": 42,
  "requested_at": "2026-10-26T10:00:00+09:00",
  "attempt": 1,
  "input": {
    "mood": "happy",
    "activities": ["cooking", "reading"],
    "place": "home",
    "companions": ["family"],
    "weather": "sunny",
    "diary_detail": "a small birthday cake with candles",
    "shot": "medium"
  }
}
```

- `input`은 `prompt_builder.py`의 앱 입력 형식과 같다 (README 4-2장).
- `job_id` = 일기 id + 버전. 같은 일기를 고쳐서 다시 요청하면 버전이 올라간다.

### 3-3. 결과 메시지 (워커 → Java)

```json
{
  "job_id": "diary-1234-v2",
  "status": "success",
  "engine": "local",
  "model": "klein-4b-distilled+mochi_lora_20261023_s2000/gguf_q4",
  "image_url": "s3://.../diary-1234-v2.png",
  "prompt": "mochi_char, happy, cooking, ..., warm children's picture-book illustration, ...",
  "seed": 123456,
  "gen_sec": 7.5,
  "queue_wait_sec": 12.0,
  "finished_at": "2026-10-26T10:00:31+09:00"
}
```

- `engine`은 `local` 또는 `api`다. 두 엔진의 그림체가 다르므로(9장) **반드시 저장한다.**
- 실패하면 `status: "error"`와 `error` 문자열을 담는다.

### 3-4. 중복과 순서

- 워커는 **업로드가 끝난 뒤에** ack를 보낸다. 생성 중에 노트북이 죽으면 메시지가 큐로 돌아가 다시 처리된다.
- 그래서 같은 `job_id`의 결과가 **두 번 올 수 있다.** Java는 먼저 도착한 결과를 쓰고 나중 것은 무시한다.
- 일기를 수정해 버전이 올라가면, 예전 버전의 결과는 무시한다.

## 4. 대체(fallback) 규칙

| 상황 | 동작 | 누가 판단 |
|---|---|---|
| 노트북 정상, 큐 비어 있음 | 노트북이 처리 | – |
| 노트북 heartbeat가 90초 넘게 없음 | 처음부터 `image.api`로 보냄 | Java |
| 일이 밀려서 60초 안에 못 가져감 | TTL이 지나 자동으로 `image.api`로 이동 | RabbitMQ |
| 노트북이 처리하다 죽음 | 메시지가 큐로 돌아감 → 다시 TTL 대상 | RabbitMQ |
| 노트북에서 생성 오류 | `attempt` +1 후 `image.api`로 다시 보냄 | 노트북 워커 |
| API도 실패 | 3번 재시도 후 `image.dlq`로 이동, 사용자에게는 "이미지 준비 중" | API 워커 |

**판단은 항상 켜져 있는 쪽(Java, RabbitMQ)이 한다.** 노트북이 죽으면 노트북 스스로는 아무것도 판단할 수 없기 때문이다.

60초와 90초는 임시값이다. 사용자가 이미지를 기다릴 수 있는 시간에 맞춰 정한다 (9장).

## 5. 노트북 워커 처리 흐름

### 5-1. 왜 "묶어서" 처리해야 하나

6GB에서는 텍스트 인코더(8.05GB)와 트랜스포머를 **동시에 올릴 수 없다.** 그래서 지금 코드(`klein_runtime.py`)는 다음 순서로 돌아간다.

1. 텍스트 인코더를 올린다.
2. 프롬프트를 인코딩한다.
3. 텍스트 인코더를 내린다.
4. 트랜스포머를 올린다.
5. 이미지를 생성한다.

요청 1건마다 이 과정을 반복하면 로딩 시간이 생성 시간보다 길어진다. 그래서 짧은 시간 동안 들어온 요청을 모아서, **인코딩은 모아서 한 번에**, 생성은 연속으로 처리한다.

### 5-2. 처리 루프

```
시작
 ├─ 모델 파일을 RAM에 미리 읽어 둠 (디스크 로딩 시간을 줄임)
 ├─ heartbeat 스레드 시작 (30초마다 {"worker": "laptop-1", "status": "idle|busy", "queue_len": n})
 └─ 반복:
     1. image.local에서 메시지를 가져옴 (prefetch = 최대 묶음 크기 8)
        - 첫 메시지를 받으면 최대 5초 더 기다리며 모음 (또는 8건이 차면 바로 시작)
     2. 각 메시지마다 prompt_builder로 프롬프트를 만듦 (caption + inference_style)
     3. [텍스트 인코더 단계] 인코더를 올림 → 묶음 전체 인코딩 → 인코더를 내림
        - 같은 문장은 캐시(outputs/cache/te) 재사용
     4. [생성 단계] 트랜스포머(q4) + LoRA를 올림 → 한 장씩 생성
        - 한 장이 끝날 때마다: S3 업로드 → result 큐에 결과 → 해당 메시지 ack
     5. 생성 중에 새 메시지가 들어오면, 지금 묶음을 끝낸 뒤 다음 묶음으로
```

- **ack는 한 장씩 보낸다.** 묶음 중간에 죽어도, 끝난 장은 다시 처리되지 않는다.
- **prefetch 제한이 중요하다.** 노트북이 메시지를 너무 많이 가져가 쥐고 있으면, 그 메시지들은 TTL이 멈춘 채 API로 넘어가지 못한다. 묶음 크기 이하로 제한한다.
- **가져간 뒤에도 시간 제한을 둔다.** 가져간 메시지라도 `requested_at`에서 일정 시간(예: 120초)이 지났으면, 생성하지 않고 API 큐로 다시 보낸다.

### 5-3. 묶음 크기별 처리 시간

**실측 (10/23 매트릭스 실행, 768, 묶음 40건, 평가 시간 제외)**

| 실행 | 조건 | 시작 → 마지막 이미지 | 장당 |
|---|---|---|---|
| `klein_lora_fp8_768` | 인코딩 캐시 없음 (실제 서비스와 같음) | 17:18:38 → 17:29:22 (644초) | **16.1초** |
| ↳ 인코딩 단계 | 인코더 로드 13.1초 + 40개 인코딩 + 트랜스포머 로드 | 17:18:38 → 17:24:01 (323초) | – |
| ↳ 생성 단계 | 39장 | 17:24:01 → 17:29:22 (321초) | 8.2초 |
| `klein_lora_gguf_q4_768` | 인코딩 캐시 있음 (같은 문장 재요청) | 17:42:46 → 17:48:11 (325초) | **8.1초** |

**추정 (위 실측 요소로 계산, q4)**

장당 시간 ≈ (인코더 로드 13초 + 트랜스포머 로드 약 6초 + N × (인코딩 7초 + 생성 7.5초)) ÷ N

| 묶음 크기 N | 1 | 4 | 8 | 40 |
|---|---|---|---|---|
| 장당 시간 (추정) | 약 34초 | 약 19초 | 약 17초 | 약 15초 |
| 시간당 처리량 (추정) | 약 105장 | 약 190장 | 약 210장 | 약 240장 |

- 묶음을 4~8건으로 잡으면 대기 시간과 처리량 사이 균형이 좋다.
- 인코딩 7초는 인코더가 6GB를 넘어 공유 메모리를 쓰는 상태에서 잰 값이다.
- **다음 단계:** 묶음 크기 1 / 4 / 8로 실제 측정한다 (10장).

### 5-4. 운영 체크리스트

- **실험과 동시에 못 쓴다.** 학습이나 매트릭스를 돌리는 동안에는 워커를 멈춘다. 이때는 heartbeat가 끊겨 자동으로 API로 넘어간다.
- 전원 연결, 덮개를 닫아도 절전하지 않게 설정, Windows 업데이트 자동 재시작 시간대를 조정한다.
- 발열을 기록한다. 학습 때 최고 78°C, 추론 매트릭스 때 77°C였다.
- 워커 로그에 묶음 크기, 장당 시간, VRAM, 공유 메모리를 남긴다. 측정 코드는 `ResourceMonitor`(`scripts/common.py`)를 재사용한다.

## 6. API 워커

- 서버(항상 켜짐)에서 `image.api`를 소비한다.
- 같은 `prompt_builder.py`로 **긴 생성 프롬프트**(`build_prompt`)를 만든다. 감정에 맞는 anchor 이미지(`outputs/anchors/{mood}.png`)를 참조로 첨부한다.
- 후보: 학습 데이터를 만들 때 쓴 Atlas Cloud `openai/gpt-image-2.5-flare-developer/edit`.
  - 모델 페이지 기준 장당 $0.03.
  - 10/22~23 생성 65건의 장당 시간 중앙값 40.3초 (28.8~113.9초).
- 구현 위치: `scripts/providers.py`의 `ExternalApiProvider.generate()`. 공급자(`{{IMAGE_API_PROVIDER}}`)가 정해지면 채운다.

## 7. GPU 메모리와 처리량

### 7-1. 왜 6GB에서는 하나씩 올려야 하나

| 구성 요소 | 크기 | 출처 |
|---|---|---|
| 텍스트 인코더 Qwen3-4B (bf16) | **8.05GB** | HF 캐시 실제 파일 |
| 트랜스포머 bf16 / fp8 / q8 / q4 | 7.75 / 약 3.9 / 약 4.3 / 약 2.6GB | 실제 파일, README 6-1 |
| VAE | 0.17GB | 실제 파일 |
| 생성 중 최고 사용량 (768, 트랜스포머 + LoRA + VAE + 계산 공간) | q4 **4.01GB** · fp8 5.23GB · q8 5.60GB | 10/23 실측 |

### 7-2. 두 모델을 동시에 올리려면 (추정)

CUDA 기본 사용분과 Windows 화면 출력용으로 0.5~1GB를 더한다.

| 텍스트 인코더 | 트랜스포머 | 합계 | 필요한 GPU |
|---|---|---|---|
| bf16 (8.05) | q4 (4.01) | 약 12.1GB + 여유 | **16GB** |
| bf16 | fp8 (5.23) | 약 13.3GB + 여유 | 16GB |
| bf16 | bf16 (약 9+) | 약 17GB 이상 | 24GB |
| 8bit (약 4.2) | q4 | 약 8.2GB + 여유 | 12GB |
| 4bit (약 2.5) | q4 | 약 6.5GB + 여유 | 8GB 빠듯, 6GB 불가 |

- 인코더를 8bit나 4bit로 줄였을 때 화질이 어떻게 변하는지는 **아직 측정하지 않았다.**
- 16GB에서 두 모델을 상주시키면 로딩 시간이 없어진다. 그러면 장당 약 15초 이하로 예상된다(추정). GPU가 빠르면 더 짧다.
- 해당 GPU 예시: RTX 4090 Laptop (16GB), 4060 Ti 16GB, 4070 Ti Super 16GB, 클라우드 T4 (16GB), L4·A10G (24GB).

## 8. 프롬프트를 어디서 만들까

| 방식 | 장점 | 단점 |
|---|---|---|
| A. Java가 `prompt_builder`를 옮겨서 만들고, 완성된 프롬프트를 보냄 (원래 계획) | 워커가 단순함 | 규칙이 Python과 Java 두 곳에 생김. 고칠 때마다 둘 다 바꿔야 함 |
| **B. Java는 앱 입력만 보내고, 워커가 `prompt_builder.py`로 만듦 (추천)** | 규칙이 `prompt_rules.yaml` 한 곳에만 있음. 노트북과 API가 같은 규칙을 씀 | API 워커도 Python이어야 함 |

B를 쓰더라도 결과 메시지에 실제 사용한 `prompt`를 담아 보내면, Java 쪽에서 기록하고 확인할 수 있다.

## 9. 팀이 정할 것

- [ ] **사용자 대기 허용 시간:** TTL 60초, heartbeat 90초, 가져간 뒤 제한 120초를 이 값에 맞춘다.
